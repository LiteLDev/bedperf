结论

  1. 从 1 到 2 vCPU 提升最大：原生 BDS 中位数从 — 到 —。1 vCPU 时 tick 线程要和其余线程挤同一个核；从 2 vCPU 起，容量点的主线程占用都接近 100%，瓶颈变成单个 tick 线程，所以 4 vCPU 以后几乎不再增长（BDS 在 4、8、16、32 vCPU 为 —、—、—、—）。
  2. Endstone 在每一档都最高（8 vCPU 中位数 —，BDS 为 —）。Endstone 在 Linux 上预加载 mimalloc 替换了内存分配器，这个差距同时包含插件框架和分配器两个因素。
  3. Wine 本身的开销：BDS (Wine) 比原生 BDS 平均少 —（2 vCPU 起各档的平均）。LeviLamina 只有 Windows 版，这里的两个 LeviLamina 方案都跑在同一个 Wine 下，应和 BDS (Wine) 比较：8 vCPU 时 BDS (Wine) —、LeviLamina (Wine) —、LeviLamina+LeviOptimize (Wine) —。
  4. 内存不是限制：所有运行的内存峰值最多只到上限的 —（1 vCPU 的 Endstone）。Endstone 的游戏进程在 32 vCPU 时峰值 — GiB，约为原生 BDS（— GiB）的两倍，Wine 下的三个方案与原生 BDS 接近。内存随 bot 数增长很少（见资源曲线）。
  5. 重复之间的波动：1 vCPU 下最大，例如原生 BDS 三次为 —；2 vCPU 起同一组合多数只差几个 bot。差距小于范围重叠的两个方案不应看作有差异。

方法

机器
3 台 GCE n2d-standard-224（AMD EPYC 7B13，2 个 NUMA 节点，224 vCPU，896 GB），Ubuntu 22.04。
服务端 CPU
每次运行独占 N 个 vCPU：N ≥ 2 时为同一 NUMA 节点内的整个物理核（两个 SMT 线程），N = 1 为一个线程。用 systemd cgroup 的 AllowedCPUs 限定，并由 bedperf 绑核校验。
服务端内存
同一 cgroup 的 MemoryMax = 8N GiB，禁用 swap。
测量进程
每台机器预留 4 个物理核（8 个 vCPU，编号均 ≥ 64）给所有运行的编排和采样进程，服务端和 bot 都不使用。
Bot
与服务端在同一台机器，用剩余的 CPU（一个公共 cgroup，随服务端分配自动收缩），每个 worker 进程 1 个 bot。调度器按 bot CPU 预算决定同时运行的任务数，避免 bot 端饱和。
负载
bedperf standard 预设的 walk 场景：bot 在出生点半径 32 格内行走，视距 10、模拟距离 4，种子固定，关闭昼夜与天气。
爬坡
从 2 个 bot 开始，每步加 2 个；每步先等 15 秒让新 bot 加入，再测 165 秒，合计 3 分钟一步。测量窗口平均 TPS 低于 15 即停止。
有效性
bot 端饱和（worker 事件循环 p99 > 250 ms 或 worker CPU > 85%）超过测量窗口的 5%、绑核不符、TPS 两种来源不一致等，都判该步无效并在同一人数重测一次；连续两次无效则整次运行作废重跑。
版本
BDS 1.26.60.6；LeviLamina 26.60.7、LeviOptimize 0.18.0，由 lip 0.41.0 安装，跑在 lip 自带的 Wine 11.21 下；BDS (Wine) 同样由 lip 装原版 Windows 服务端；Endstone 0.11.15（Python 3.11）。bedperf 提交 a3ee0ae（PR #34、#35）。

有效性与限制

  • 实验中途修正过几处方法，详见下方运行列表的“方法”一栏：前期的 — 次运行（都是第 1 次重复）没有 15 秒等待、或每个 worker 放 2 个 bot、或用更严的 bot 饱和规则。它们给服务端的负载节奏完全相同（每 3 分钟加 2 个 bot），只是 bot 端判定更严，所以保留。
  • Wine 会把部分线程的亲和性设成 Windows 处理器组 0（宿主 CPU 0–63）。分到编号低于 64 的核的 Wine 服务端会被悄悄限制在一半的 vCPU 上，而 bedperf 的绑核校验发现不了。受影响的运行已作废并重跑，不在本页数据中，之后 Wine 服务端（N ≥ 2）只分配两个线程编号都 ≥ 64 的核。
  • vCPU 是 GCE 虚拟机的超线程。N = 1 只是半个物理核，和物理机上的“1 核”不同。
  • 多个服务端与 bot 同时跑在同一台机器上，按要求没有隔离缓存、内存带宽等共享资源；服务端之间只隔离了 CPU 和内存上限。
  • LeviLamina 只有 Windows 版。两个 LeviLamina 方案的结果包含 Wine 的开销，不代表 Windows 上原生 LeviLamina 的表现。
  • 只测了一种负载（walk、视距 10）和一张种子地图；其他负载下排名可能不同。bot 与服务端走本机网络，没有真实玩家的延迟和丢包。
  • 内存峰值只计游戏进程（Wine 下不含 wineserver 等辅助进程，Endstone 不含 Python 启动器）。
