Methodology

The headline is the largest bot count that passed every criterion in a step, taken as the median over the ok repeats, each on a fresh instance. Each repeat ramps the bot count until the first failing step, then bisects between the last pass and the first fail. Steps measured while the load generator was saturated are invalid rather than failed.

  • Repeat status. A repeat is ok, server_failed (the server crashed, was stopped by a watchdog or ended the repeat early: a result about the server, shown as k/n ok, never dropped silently) or invalid (never ended, search unfinished, or flagged by the harness: says something about the harness or machine). Only ok repeats enter the median, the mean curves and the per-player fits.
  • TPS comes from the Script API probe: ticks per ~1 s window, measured inside the server tick.
  • Main-thread utilisation is the CPU share of the busiest server thread (OS sampling). Because BDS sleeps out the rest of each 50 ms tick it approximates MSPT / 50 ms. It cannot separate lock waits from sleep and does not include work offloaded to other threads.
  • Per-player figures are least-squares slopes over the step means of all repeats. Utilisation is fitted on passing steps when possible, because it flattens near 1.0 once the tick thread is saturated. "Players at util 1.0" extrapolates that fit.
  • RSS per player in the scaling chart is (RSS − fitted zero-player RSS) / players, so the fixed server baseline does not dominate low player counts. It converges on the memory-per-player slope.
  • RTT is the tick-bound round trip of a scripted ping as seen by the bots, i.e. client-perceived lag.
  • The timeline is downsampled for size. TPS shows the minimum of each bucket so dips stay visible.
