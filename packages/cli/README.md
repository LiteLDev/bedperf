# @bedperf/cli

The `bedperf` command. It wires every package together: bds-install creates the instance, bds-process runs it, probe-addon and sysmon measure it, loadgen and scenarios supply the bots, the orchestrator runs the search, and report writes the result.

```bash
corepack pnpm bedperf run --scenario walk                      # quick preset, 5→50 bots
corepack pnpm bedperf run --preset standard --scenario build --set ramp.max=200
corepack pnpm bedperf run --config my.json --dry-run           # print the resolved config
corepack pnpm bedperf run --configs a.json,b.json --order rotate # A/B session, repeats interleaved
corepack pnpm bedperf run --machine-profile box.json            # placement profile for this machine
corepack pnpm bedperf run --server levilamina-levioptimize      # another server implementation (see below)
corepack pnpm bedperf run --agents 10.0.0.21:19260 --bot-target-host 10.0.0.10   # bots on a remote agent
corepack pnpm bedperf agent --listen 0.0.0.0:19260 --placement auto              # on a bot machine
corepack pnpm bedperf report runs/<id>
corepack pnpm bedperf analyze runs/<id> [--write]               # recompute steps from samples.jsonl
corepack pnpm bedperf compare runs/<a> runs/<b> -o compare.html
corepack pnpm bedperf install latest --accept-eula
corepack pnpm bedperf install --server endstone --accept-eula   # install a server flavor ahead of a run
corepack pnpm bedperf scenarios
```

## What `run` adds on top of the orchestrator

- **Versions.** `bdsVersion` (`latest`, `preview` or `x.y.z.w`) is resolved to a concrete build and downloaded only if it is not cached. A download needs `--accept-eula`. The bot protocol family is derived from the build (BDS 1.26.63.1 → `1.26.60`) unless `botVersion` is set. Both concrete values are recorded in `config.json` and `meta.json`.
- **Server implementation.** `--server <preset>` sets the config's `server` section to one of core's `SERVER_PRESETS`: `bds` (the default when the section is absent), `levilamina`, `levilamina-levioptimize`, `endstone`, `bds-wine`, `levilamina-wine`, `levilamina-levioptimize-wine`; `--set server.versions.levilamina=26.60.7` (also `levioptimize`, `endstone`; values stay strings) and `--set server.loaderConfig.<path>=<value>` refine it. The build comes from `@bedperf/bds-install`'s `ensureServer`: vanilla keeps the BDS fast path (a cached build needs no flag), a modded flavor already installed (complete marker in `<cache>/servers/`) needs no flag either, anything that downloads needs `--accept-eula`. Modded flavors run BDS 1.26.60.6 (`bdsVersionFor`) unless `bdsVersion` is exact; the bots use family 1.26.60. Wine runs only on a Linux host and native LeviLamina only on Windows (usage error, exit 2, naming the preset to use instead). The run dir is named `<config>-<server>` (e.g. `quick-levilamina-levioptimize`); the config name itself is unchanged, so runs of the same benchmark on different servers compare as an implementation comparison (`bedperf compare a b c`).
- **Launchers.** Each instance is created from the installed build and started with its `LaunchSpec` (LeviLamina's `bedrock_server_mod.exe` directly or under lip's Wine, Endstone through its Python CLI). Everything that measures the server uses the game process (`BdsProcess.pid` once started), never the launcher: the OS sampler, the tick-thread lookup and placement verification. The interference sampler's `server` group also holds the launcher (with its descendants) and helpers outside the tree (`auxPids()`, e.g. wineserver), refreshed before every hold.
- **Scenarios.** `scenario.module` may be a registry name (`walk`), the alias `@bedperf/scenarios/walk`, or any module URL. The scenario's `serverSetup` runs once after the server starts.
- **Server properties.** Layers apply in this order: `REQUIRED_BOT_PROPERTIES` < `bench-default` < the config's `serverProperties` and `world`. A config that overrides a required property (for example `online-mode=true`), or sets the port or level name, is rejected. Scenarios that send commands as bots get `default-player-permission-level=operator`.
- **Instances.** Each repeat gets a fresh instance with the probe pack installed. Instances are deleted afterwards unless `--keep-instances` is given. The BDS output goes to `runs/<id>/bds.log`, or `bds-r<n>.log` when there are several repeats (or a rerun).
- **CPU placement.** With `placement.enabled` (the default) the run plans the server / bot / harness CPU sets once (`@bedperf/placement`, profile from the config's `placement` section, which `--machine-profile <file>` overrides with a `{label, placement, gates}` profile and `--set placement.*` overrides again). A plan with a failing check refuses to run (exit code 3); set `placement.enabled=false` to run unplaced. The harness process is placed on the harness set; on Linux the server's launcher starts under `taskset`/`nice` (every descendant inherits it: Wine's game process and wineserver, Endstone's Python and its `bedrock_server`); on Windows the plan is applied to the launcher right after the spawn (children it creates later inherit the mask) and again to the game process as soon as it is identified, before `start()` resolves; every loadgen worker is put on the bot set as it is forked. The engine verifies the server at ready and at every hold start and end: the game process fully (every thread, priority), a separate launcher and helpers (wineserver) for affinity (`verifyServerProcesses`); a member that has exited is not a violation.
- **Gates.** Before every repeat the machine must be idle for `gates.idleSec` (15 s) on the server CPUs (`--skip-idle-check` skips this). A busy machine before the first repeat stops with exit code 3 and lists the busiest foreign processes, before any run dir exists. The interference sampler, the `time query gametime` sampler and the OS sampler run for the whole repeat (see the orchestrator README for what they gate).
- **Bot agents.** `--agents host:port,...` (or `agents` in the machine profile) runs the bots on `bedperf agent` processes on other machines, authenticated with `$BEDPERF_AGENT_TOKEN`, and `--bot-target-host` is the address of this machine their bots dial (required, and not loopback, when an agent is on another machine). The server machine is then planned in `remote-bots` mode (no bot CPU set), every agent is idle-checked with this machine before each repeat, and the topology is recorded in `meta.json` `topology`, not in `config.json`. `bedperf agent` (options in `--help`) serves those sessions on a bot machine. See [docs/distributed.md](../../docs/distributed.md).
- **Sessions.** `--configs a.json,b.json` runs every config in one session: `runs/<session>/session.json` plus one run dir per config inside it. `--order rotate` (default) runs repeat k of every config in block k, starting at config k mod n; `sequential` runs each config's repeats in a row; `seeded:N` shuffles each block with seed N. `--set` and `--machine-profile` apply to every config.
- **Exit codes.** 0: at least one repeat `ok`; 2: usage or config error; 3: environment gate (busy machine, unusable placement, machine lock held); 4: every repeat `server_failed`; 5: no `ok` repeat (some `invalid`); 130: interrupted; 1: anything else. A session exits with its worst run.
- **`analyze <runDir>`** recomputes every step from `samples.jsonl` and `config.json` through the engine's own code path, compares it with `steps.json` (canonical form: sorted keys, numbers rounded to 4 decimals, LF) and checks `meta.json`'s file manifest. It prints `unchanged` or `differs` (exit 1, listing the steps); `--write` rewrites `steps.json` and its manifest entry.
- **Machine lock.** Only one measured run per machine: two benchmarks sharing a CPU measure each other. `run` creates the lock file `$BEDPERF_LOCK`, or `machine.lock` in the cache root (`%LOCALAPPDATA%\bedperf\cache`, `~/.cache/bedperf` or `BEDPERF_CACHE_DIR`), before resolving or downloading BDS, and removes it when it finishes, fails, or exits after a second Ctrl+C. A second `run` fails at once, naming the holder's pid, run id and start time. A lock left behind by a process that was killed hard is taken over once its pid is gone. Benchmarks that share a machine must share the lock file. `--no-lock` skips it (for runs whose numbers you do not care about).
- **Provenance.** `meta.json` records the server build (`meta.server`: spec, label, BDS version, artifacts with sha256, build hash, allocator, effective loader config, notes) and its artifacts again under `artifacts.server`, the BDS zip sha256 (the build's `bds` artifact: the bds-install sidecar, or lip's cached zip for LeviLamina), the probe pack tree hash, the bedboo commit, the config hash and `benchConfigSha256` (the config without `server`), a machine fingerprint and the bedperf commit; meta.json and config.json are scrubbed of absolute paths, user and host names (see the orchestrator README). `config.json` holds the resolved server spec (pinned versions filled in).
- **Interrupts.** The first Ctrl+C stops after the current step and still cleans up. A second Ctrl+C, or SIGTERM, stops every running server now (graceful `stop`, killed after 8 s, the whole tree and `wineserver -k` for Wine), deletes the instance dirs and exits with 130. This matters on Linux, where a launcher-started server runs in its own process group and never receives the terminal's Ctrl+C.
